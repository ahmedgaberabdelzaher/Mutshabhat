# Data model, review statuses and build flavors (QMT-48 / DAT-09)

## Status lifecycle

```
draft (مسوّدة) ──submit──▶ under_review (قيد المراجعة) ──approve──▶ approved (معتمد)
                                                       └─reject───▶ rejected (مرفوض)
approved ──edit (any data or highlight-rule change)──▶ under_review
```

- Implemented in `src/domain/review-status.ts` (`applyReviewAction`). Invalid transitions throw.
- Every transition/edit bumps `review.version` and records `decision` (اعتماد / تعديل / رفض), `decisionReason`, `reviewer`, `reviewedAt` (ISO-8601; shown in Asia/Riyadh).
- Legacy QMT-20 names: جديد → draft; موسوم / بانتظار المراجعة → under_review.

## Similarity type: lafzi vs semantic

The MVP covers **verbal (لفظي) mutashabihat** only. Every pair and group carries `similarityType`:

- `lafzi` — the two ayahs share most of their wording and differ in a few words/letters.
- `semantic` — little shared wording and no shared phrase of ≥ 3 consecutive words (similar meaning / theme). Kept in the review dataset for the committee, **hidden from the default view** (records list, ayah analogues, browse positions) and listed only when the reviewer picks «تشابه معنوي» in the similarity filter. In the review build they show «لا يتوفر تحديد دقيق لموضع الاختلاف» because no word-level highlight applies.
- **Committee pilot exception (review build only):** all 285 HifzLink pilot pairs are listed in the default view whatever their type, each with a type badge (لفظي / معنوي). Every analogue and record in the review build carries this badge.

Where it lives: `highlightRules[].similarityType` (pair level, authoritative) and `groups[].similarityType` (group level: `lafzi` if at least one pair is lafzi). A pair without a rule inherits its group's type. The classification rule itself is defined with the auto-diff (QMT-26) further down / in `scripts/lib/auto-diff.mjs`.

Beta/production guarantees (tested in `mutashabihat-repository.test.ts`):

1. A group must be **explicitly** `similarityType: "lafzi"` to be shown; untagged or `semantic` groups are dropped even if `approved`.
2. Any rule tagged `semantic` (any status) blocks that pair, even inside a lafzi group.
3. The `semantic` filter is not offered and returns nothing.

`EXPO_PUBLIC_APP_FLAVOR` = `review` | `beta` | `production` (default **production**, the safe choice).

| Flavor | Dataset | Visible statuses | Status badge | EAS Update channel | iOS / Android id |
| --- | --- | --- | --- | --- | --- |
| review | review | draft, under_review **and approved** (so the committee can revisit approvals) — never rejected | yes | `review` | `com.ahmedgaber.mutshabhat.review` |
| beta | production | approved | no | `beta` | `com.ahmedgaber.mutshabhat.beta` |
| production | production | approved | no | `production` | `com.ahmedgaber.mutshabhat` |

Defence in depth:

1. **Bundle level** — `src/data/datasets.ts` only `require`s the review JSON when the bundle is built for `review`; Metro drops it from beta/production bundles. `npm run check:production-bundle` exports all three web bundles and fails if candidate data appears outside the review bundle.
2. **Repository level** — `LocalMutashabihatRepository` refuses a dataset whose `kind` doesn't match the flavor and filters records by the flavor's visible statuses and allowed similarity types (beta/production: explicit `lafzi` only) before anything reaches the UI.

## List titles (mutashabihat lists)

Every list of mutashabihat items — ayah analogues, records screen, browse positions (surah / juz / page) — titles each item with **the similar word/phrase itself**, in the Quran font. The details (surah name, ayah number, positions, badges) stay on the item below the title, and tapping behaves as before.

Titles are **data**, generated by `npm run build:mutashabihat` (`scripts/lib/auto-diff.mjs`) and editable by the committee (set `titleBasis: "committee"`; ships as OTA, no rebuild):

- `highlightRules[].titles` — one `TitleSpan` per side `{ ayahId, startWord, endWord, text }`, each side in its own exact wording (e.g. جَنَّٰتٍ / جَنَّٰتٌ). Each list item shows the span of the ayah it represents.
- `groups[].title` (+ `titleBasis`, `titleCoverage`) — used by the records screen.

`text` is always `words[startWord..endWord].join(' ')` of one Tanzil ayah, i.e. an **exact substring** of the unmodified text (tested for every rule and group in `datasets.test.ts`). The Quran text itself is never changed.

Rules (`meaningfulSharedSpan`, `extendToTwoWords`, `isTitleStopword`, `findKeySequence` in `src/domain/diff.ts`; applied by `scripts/lib/auto-diff.mjs`):

1. **Shared part.** Find the longest common contiguous run of words between the two ayahs (letter-only keys; inside one ayah per side so the text is a substring of that ayah) **that contains at least one meaningful word**. A word is *not* meaningful if its undiacritised form (comparison key, alef forms unified, ى→ي, optionally with one leading و/ف) is in `TITLE_STOPWORDS`:
   - prepositions: من، في، على، إلى، عن، مع، حتى، لدى
   - particles: ما، لا، لم، لن، ليس، هل، إن/أن، إذ، إذا، لو، لولا، إلا، يا، كي، لما، أما، ثم، أو، أم، قد، بل، لكن، إنما، كما، بما، مما، ممن، عما، فيما
   - relative / demonstrative pronouns: الذي، التي، الذين، اللاتي، اللائي، ذلك، ذلكم، هذا، هذه، تلك، أولئك، هؤلاء
   - personal pronouns: هو، هي، هم، هن، هما، أنا، نحن، أنت، أنتم
   - preposition + pronoun suffix: له، لها، لهم، لكم، لنا، به، بها، بهم، فيه، فيها، فيهم، منه، منها، منهم، منكم، عليه، عليها، عليهم، عليكم، إليه، إليهم، إليك، عنه، عنها، عنهم … (full list in code)

   A run may still contain particles (e.g. «مِن دُونِ ٱللَّهِ»); it just needs one meaningful word. If a particle-only run at least as long as the chosen one was skipped (e.g. «إِنَّ فِى ذَٰلِكَ» in 16:11 ~ 30:21 → «لِّقَوْمٍ يَتَفَكَّرُونَ»), `titleMethod` is `meaningful_word`.
2. **Minimum 2 words.** If the shared part is one word, each ayah's title is extended with the adjacent word **from that ayah's own text**: the **following** word (it shows where the two ayahs part ways right after the shared word, e.g. 2:2 «هُدًى لِّلْمُتَّقِينَ» / 27:2 «هُدًى وَبُشْرَىٰ»); if the shared word ends the ayah, the **preceding** word (101:6 «ثَقُلَتْ مَوَٰزِينُهُۥ» / 101:8 «خَفَّتْ مَوَٰزِينُهُۥ»). A one-word ayah (e.g. «الٓمٓ») stays one word. `titleMethod`: `extended` (or `meaningful_word_extended`).
3. **Fallback.** Only when the two ayahs share **no meaningful word**: first 5 words of each ayah, shown with «…» and the type badge. `titleMethod: fallback`.

`titleBasis` still records the pair's diff method (`phrase` / `lcs` / `fallback`); `titleMethod` records how the title was derived (`shared` / `extended` / `meaningful_word` / `meaningful_word_extended` / `fallback`; `committee` after a manual edit). All generated titles belong to rules with `status: "draft"`, so the committee reviews and can edit them.

**Groups with more than 2 members:** candidates are the shared (meaningful) parts of all pairs in the group — before the per-ayah extension. For each candidate, count the members that contain it (letter-only keys, contiguous, inside one ayah); it must be found in ≥ 2 members. Ranking: multi-word candidates first (a lone word found in more members loses to a phrase), then the most members, then more words. The title is taken from the first member (group order) that contains it and, if one word, extended from that member's own ayah as above. No candidate → fallback (beginning of the first member). Example: `waqar144:2:34` (7 ayahs) → «إِلَّآ إِبْلِيسَ», found in all 7. Two-member groups get their pair's shared part. Positions (browse lists) use the title of their first (primary) analogue, in the position ayah's wording.

Counts (review dataset v1, 6,830 pairs / 2,928 groups):

| `titleMethod` | pairs | groups | pilot groups |
| --- | --- | --- | --- |
| shared | 4,739 | 2,750 | 251 |
| extended | 565 | 51 | 11 |
| meaningful_word | 34 | 20 | 0 |
| meaningful_word_extended | 735 | 53 | 7 |
| fallback | 757 | 54 | 16 |

## Swapping data without a rebuild

Screens read only through `MutashabihatRepository` (`src/data/mutashabihat-repository.ts`). The datasets and highlight rules are JSON in the JS bundle, so a new dataset version ships as an **EAS Update** to the matching channel (`npm run update:review` / `npm run update:production`) with no native rebuild. A later API-backed repository can replace the local one without touching screens.

## Highlight rules (QMT-26)

Highlighting is data-driven: `highlightRules[]` in the dataset, one rule per pair of ayahs (`pair`, ordered by mushaf position).

```jsonc
{
  "id": "auto:2:2|27:2",
  "pair": ["2:2", "27:2"],
  "ranges": [{ "ayahId": "2:2", "startWord": 6, "endWord": 6 }, { "ayahId": "27:2", "startWord": 1, "endWord": 2 }],
  "letterRanges": [{ "ayahId": "…", "word": 3, "start": 5, "end": 7 }], // optional, UTF-16 offsets inside a word
  "granularity": "word",          // word | letter | none (identical texts, or a semantic pair)
  "similarityType": "lafzi",      // lafzi | semantic (see classification rule below)
  "source": "auto_diff",          // or "committee"
  "algorithm": "lcs-word-v1",
  "method": "lcs",                // lcs | phrase (lafzi rules only)
  "titles": [                     // list title, one span per side (pair[0], pair[1]), each in its own wording
    { "ayahId": "2:25", "startWord": 7, "endWord": 11, "text": "جَنَّٰتٍ تَجْرِى مِن تَحْتِهَا ٱلْأَنْهَٰرُ" },
    { "ayahId": "3:15", "startWord": 9, "endWord": 13, "text": "جَنَّٰتٌ تَجْرِى مِن تَحْتِهَا ٱلْأَنْهَٰرُ" }
  ],
  "titleBasis": "phrase",         // phrase | lcs | fallback | committee
  "titleMethod": "shared",        // shared | extended | meaningful_word | meaningful_word_extended | fallback | committee
  "phrases": [ … ],               // method=phrase only: [{ a: WordRange[], b: WordRange[], length }]
  "confidence": "medium",         // high | medium | low (low = little overall overlap: semantic, or lafzi via phrase) — persisted uncertainty
  "matchRatio": 0.14,
  "type": "إبدال",                 // relative to pair[0]; only when the pattern is unambiguous
  "status": "draft",
  "review": { "version": 1 }
}
```

- Word indexes refer to Tanzil tokens (`text.split(' ')`); the app renders spans over the unchanged string (`src/domain/highlight.ts`), and a test re-joins every rule's segments to the exact text.
- `npm run build:mutashabihat` regenerates auto rules with `src/domain/diff.ts`: word LCS on letter-only keys (diacritics, Quranic marks and alef forms ignored for matching), differences inside the aligned region plus edge substitutions, letter ranges for diacritic-only differences and 1↔1 similar-word substitutions.
- **Classification rule (lafzi vs semantic)** — `similarityOf()` in `src/domain/diff.ts`. Words are compared by letter-only keys (diacritics, Quranic marks, alef forms ignored). A pair is **`semantic`** only when BOTH hold:
  1. little shared wording by word LCS: no shared word, or exactly one shared word while the shorter side has more than 4 words, or shared words < 30% of the shorter side's words; **and**
  2. no shared contiguous phrase of **≥ 3 consecutive words** (`MIN_PHRASE`).

  Everything else is **`lafzi`**, generated by one of two methods (both `source: "auto_diff"`, `status: "draft"`):
  - `method: "lcs"` (`algorithm: lcs-word-v1`) — enough overall overlap: whole-ayah word LCS as above.
  - `method: "phrase"` (`algorithm: phrase-anchor-v1`, `phraseDiff()`) — low overall overlap but a shared phrase of ≥ 3 words. It locates up to 3 shared phrases (longest first, non-overlapping), stores them in `phrases`, highlights diacritic-only differences inside each phrase at letter level, and compares the **2 words before and after** each phrase on both sides: words that don't match there are highlighted (letter ranges too for a 1↔1 similar-word substitution). The rest of each ayah is context and is not highlighted. Example 2:25 ~ 3:15: shared «جَنَّٰتٍ/جَنَّٰتٌ تَجْرِى مِن تَحْتِهَا ٱلْأَنْهَٰرُ»; highlighted «أَنَّ لَهُمْ» / «عِندَ رَبِّهِمْ» before and «كُلَّمَا رُزِقُوا۟» / «خَٰلِدِينَ فِيهَا» after, and the case ending of جنات at letter level.

  Semantic pairs get a rule with `similarityType: "semantic"`, `confidence: "low"`, no `method`, `granularity: "none"` and no ranges (no false precision); the review build shows «تشابه معنوي … لا يتوفر تحديد دقيق لموضع الاختلاف». A group is `lafzi` if at least one of its pairs is lafzi, else `semantic`. The committee can reclassify a pair by editing `similarityType` on its rule (data change, OTA).
- Counts in review dataset v1 (6,830 pairs): **3,982 lafzi** (3,063 `lcs` + 919 `phrase`) / **2,848 semantic** pairs; groups 2,684 lafzi / 244 semantic. Pairs per source (a pair counted under every source listing it): HifzLink 256 / 29, Waqar144 1,246 / 242, Quranpedia 3,314 / 2,673. Groups per source: HifzLink 256 / 29, Waqar144 1,285 / 63, Quranpedia 1,143 / 152. HifzLink pilot pairs: 256 lafzi (253 lcs + 3 phrase) / 29 semantic — all 285 visible by default in the review build.
- Group members keep `differenceRanges: []` because no licensed source provides ranges; pairwise ranges live in `highlightRules`.
- The committee corrects a rule by editing its ranges (→ `source: "committee"`, version + 1, status per the lifecycle). Shipping the edited JSON is an OTA update — no app rebuild.
- Beta/production only use rules whose status is `approved`.
